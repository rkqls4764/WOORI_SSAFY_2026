데모와 운영의 경계

이 데모에서 무엇이 모의이고, 운영으로 갈 때 어느 자리에 무엇이 연결되는지 정리한 그림입니다. 통제 로직(승인 게이트·계획 해시·멱등키·상태 머신·숫자 검증·감사 로그 형식)은 그대로 두고, 바깥과 맞닿는 자리(인증·세션·기관 연동·저장소)만 바꿉니다.

데모 지금 코드에서 모의로 채운 부분 운영 운영 전환 때 연결할 것(미구현) 그대로 데모와 운영이 같은 코드

승인에서 실행·기록까지

① 고객 인증

고객 · 화면에서 직접
데모 · MockAuthenticator'인증하고 승인하기' 버튼만 확인. 본인 확인 없음
운영 · 인증 어댑터 교체로그인 세션의 본인 인증(생체·인증서) + 계획 해시 전자서명

② 승인 토큰

시스템
그대로토큰을 세션과 계획 해시에 묶음. 계획이 바뀌면 해시가 달라져 기존 승인은 무효
데모세션 = 브라우저 쿠키, 서버 메모리 보관
운영세션 = 로그인 고객, 저장소·만료·폐기 관리

③ 실행 게이트

시스템 · LLM은 통과 판단을 하지 않음
그대로토큰 검증(발급자·세션·해시) → 통과할 때만 신청. 같은 계획·같은 항목은 한 번만(멱등키)

④ 기관 연동

InstitutionAdapter · submit / poll
데모 · DemoSimulator접수는 메모리에만, 결과는 사전에 정한 시나리오(관리비 변경 실패 포함)
운영 · 기관별 어댑터계좌이동서비스 공식 절차, 기관 직접 변경, 회사 급여 담당 전달

⑤ 감사 이벤트 로그

시스템 · 추가만 가능
그대로계획 버전·해시, 승인, 차단, 실행 요청, 결과 수신, 후속 조치를 해시 체인으로 기록
데모메모리 + JSONL 파일
운영변경 불가 저장소·감사 DB, 보존 기간·접근 통제
LLM의 자리 · LLM은 ①~⑤ 어디에도 없습니다. 도구를 고르고 결과를 설명하며, 모호하면 되묻습니다. 승인은 고객이 화면에서, 실행은 시스템이 승인 토큰으로 합니다. LLM이 실행 도구를 부르더라도 ③ 게이트가 토큰을 검증하므로 승인 없이는 차단됩니다.

어댑터 인터페이스

기관 연동 · InstitutionAdapter

Agent와 도구는 이 두 함수만 압니다. 시뮬레이터를 실제 어댑터로 바꿔도 계획·승인·실패 대응 흐름은 그대로입니다. 
submit(item_id, action, idempotency_key,
       approval_token, on_date) -> 접수증
poll(until) -> [ResultEvent(date, item_id,
       new_state, channel, message)]

인증 · Authenticator

승인 API는 계획 해시만 비교하지 않고, 인증 어댑터가 발급한 토큰을 실행 직전에 다시 검증합니다. 
authenticate(session_id, plan_hash,
       plan_version, at) -> 승인 토큰 | None
verify(token, session_id, plan_hash) -> bool

데모가 보여 주는 것과 보여 주지 않는 것

보여 주는 것

  • 승인 없이는 실행되지 않고, 계획이 바뀌면 다시 승인해야 한다
  • 숫자는 시스템이 계산하고 LLM 답변 속 숫자는 도구 결과와 대조한다
  • 기관 결과가 실패로 돌아와도 상태 머신과 대안 제시가 동작한다
  • 모든 단계가 감사 로그에 남고, 로그만으로 '승인 없는 실행 0건'을 확인할 수 있다

보여 주지 않는 것

  • 실제 본인 인증, 실제 기관 통신, 실제 고객 데이터
  • 다중 서버·장애 복구·동시 요청 처리
  • 기관별 실제 처리 기간(자동납부 3영업일은 가정)
  • 실제 거래 데이터에서의 탐지 정확도(평가는 가상 고객 기준)
